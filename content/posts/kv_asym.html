GQA shares your K and V heads. But which half is actually doing the work?

Grouped-Query Attention reduces the KV-cache by letting multiple query heads share a smaller set of key/value heads. In standard GQA, keys and values are compressed together. But they play different roles: keys help determine where to look, while values determine what information gets brought back. If those roles have different capacity requirements, the two sides may not need the same number of heads. We tested whether one side can be compressed more aggressively than the other.

01

Where we start: GQA

In standard multi-head attention, every query head gets its own key and value head. MQA (Shazeer, 2019) takes the opposite extreme: all query heads share a single key and value head — big memory win, some quality cost. GQA (Ainslie et al., 2023) sits in between: it groups query heads so each group shares one key/value head. It became the default because it keeps most of MHA's quality with far less KV-cache.

One design choice is usually left unchanged: GQA allocates the same number of heads to keys and values. But the two tensors serve different functions, so there is no obvious reason their head counts must be reduced at the same rate.

02

The question we asked

In a dot-product attention block, the two tensors have different roles:

KEYS (K)

Help compute the attention weights — where each position should look. They determine the lookup or routing pattern.

VALUES (V)

Contain the content combined using those attention weights and passed to the output. They determine what information is retrieved.

THE BET

If K requires fewer heads than V, then a model that preserves more V heads should outperform one that preserves more K heads, even at the same parameter count.

Can we compress the keys or the values — and which one is cheaper to throw away?
We held the rest of the setup constant and changed only the K/V allocation. The parameter-matched comparison uses one model with 4 key heads and 1 value head, and another with 1 key head and 4 value heads. Both have the same total number of heads and parameter count, allowing us to isolate the effect of the allocation.

How we tested it

We implemented an attention component in which n_k_heads and n_v_heads can be set independently. We evaluated five configurations, each with three seeds, on two datasets: one for general language modelling and one for targeted recall.

05

What it means

Across the two datasets, the asymmetric comparison favors the model that preserves more value heads and compresses its key heads. The size and reliability of that advantage differ by dataset, but the results suggest the two sides are not equally sensitive to head reduction:

In these experiments, keys are the cheaper side to compress. A shared key head appears sufficient for the routing patterns tested here. Values are more sensitive to head reduction. Reducing their number has a larger effect on the recall task. The practical implication is to preserve V capacity when allocating a limited KV-head budget.

Two honest caveats, because a good result should name its own limits:

① On general language modelling the effect is small — 0.8412 vs 0.8434 bpb, which is inside the ±0.003–0.005 seed noise. It's the right direction, but not yet statistically separated from luck. ② Balance still matters — the symmetric GQA 2/2 variant is the best compressed one on TinyStories, better than both asymmetric splits. So "V is more valuable" doesn't mean "throw away all the K heads"; it means K is the side you can afford to spend first.

06

The answer

conclusion

The two sides do not need to be compressed equally. Compress K more. Preserve V capacity.

At equal parameter counts, the 1-key / 4-value configuration performs better than the 4-key / 1-value configuration on both benchmarks, with a clearer difference on the associative-recall probe. In this setup, reducing K heads is less costly than reducing V heads. If you have to allocate the KV-head budget asymmetrically, these results favor preserving more value heads.

The result is consistent in direction across the two datasets, but the general-LM difference is within seed noise. A larger model, longer training, more seeds, and longer context lengths are needed to determine how robust the effect is.
